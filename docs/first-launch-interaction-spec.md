# First-launch interaction specification — from outcome backward

**Evidence labels:** `OBSERVED_PUBLIC` means directly inspected in public official product pages/docs or public UI. `DOCUMENTED_OFFICIAL` means stated in vendor documentation. `INFERRED` means product-design synthesis, not a claim about private live screens. `APT_SOURCE` means read in this repository; no workspace session was available at the time of audit.

**Scope:** First launch is not “ship every module.” It is one useful undertaking from a grounded need through a scoped commitment to a clearly reported and reviewable outcome, without presenting a participant report as verified institutional truth. The interaction target assumes persistent, authorized records eventually exist; the current implementation is a local in-memory prototype and does not meet that target.

## APT-LABS source audit: why the current workspace feels “slop adjacent”

This is not a palette problem. It is a **consequence and density problem**: the chrome promises an enterprise network, but the primary screen lacks records, ownership, state-changing feedback, and task continuity.

### P0 — fix before calling first launch competitive

1. **The primary promise is not delivered:** `CoordinationService` creates a new in-memory `JourneyStore`; `accountId` is literal `'demo'`. Commons and Workbench explicitly say local/session-only; refreshing loses work; a second user cannot see it. (`libs/shared/state/src/coordination.service.ts`, Commons, Workbench) `APT_SOURCE`.
2. **Action authority is fictional:** Workbench's “Record commitment” calls `acceptNeed` with the same `accountId` as provider; no other participant or server mandate is resolved. `fulfilNeed` records free-form reported outcome. This is a demo transition, not collaboration or authorized acceptance. (`pilot.component.ts`, `commitment-journey.ts`) `APT_SOURCE`.
3. **No record-centric studio:** the journey view shows an illustrative relationship graph, a three-step chain, evidence-ID strings, and a short event list; it lacks a reusable record header, source/authority, chronology details, revision context, related records, query/filter, or next-action owner. `APT_SOURCE`.
4. **The shell has controls without semantics:** Inspector displays basic family/type and a pseudo-ordered evidence ladder; `close()` is empty. Network row opens/inspects and navigation actions are empty methods, the page says records aren't loaded, and the table is nonetheless presented. Workbench labels commissioner “Not recorded.” `APT_SOURCE`.
5. **False operational signals are avoidable:** Home is statically zero-counted and route variants duplicate UI state. Records shows local-only warning but has a possibly misleading “Open Roll” button whose route is another filter. Never use metrics for decoration. `APT_SOURCE`.

### P1 — make it feel authored rather than assembled

- Define one interaction grammar: **queue/table on the left or main canvas; selected record and links in a right inspector; explicit next action in a stable action area; history and evidence within the record**. Only show inspector when a record is selected. On mobile it becomes a dismissible sheet with working close, Escape and focus restoration.
- Use a single precise type scale and spacing/layout grid; remove loud section labels, status chips that duplicate headings, rounded container on every region, and hard-coded pale borders that break the warm ivory/forest/brass system. The existing CSS repeats its own primitives and uses `#f3f4f6` despite the theme tokens. Compare `/workspace/workbench` and `commons.component.ts` source before visual polish.
- Replace the abstract standalone graph as hero with a human-readable undertaking summary and relationship list; graph becomes a switchable “Connections” view, because the first user task is coordination, not graph exploration.
- Use named status, not a universal maturity ladder. An outcome should read “Reported by X · date · evidence not independently assessed”; an official acceptance must be a separate attributed action with its own authority basis.
- Bring shared controls into deliberate hierarchy: search/scope, useful filters, sort, columns only when helpful, saved/current view indication; table rows must be keyboard-operable and not hide their action buttons.
- Copy the best micro-interaction ideas without mimicry: persistent list context (Salesforce), explicit action/recovery (OpenFn), relation-aware detail (Foundry), contextual queues (ServiceNow), reflowing forms (Power Apps), resumable records (CommCare), and history (Frappe).

## First-launch task, described as experience not architecture theater

**User story:** A community organization posts a clearly scoped need. A separate capable participant sees it in an appropriate queue, offers a specific commitment, the authorized commissioner accepts it, the participant reports delivery with evidence references, and an authorized reviewer records a distinct assessment or asks for correction. Both users can reopen the undertaking later and understand who did what, when, under which authority, what is only reported, and what remains unresolved.

### Interaction contract (prototype / acceptance-test target)

1. **Enter via “Work”/assigned or discoverable needs.** Show real scope, location/time context where applicable, requested capability, visibility, commissioner source/standing, created/updated times, and status. Empty, loading, forbidden, offline, service-down, and stale states say what happened. Do not show zero metrics as a dashboard.
2. **Open a need.** Keep search/filter/list context; detail contains summary, provenance/visibility, related capability/resource/place links, current commitments, activity, and valid next action. Every related entity link opens in context, never a disconnected duplicate record.
3. **Offer/commit.** Participant submits specific scope, availability/terms, and optional evidence links. Validate inputs; preserve draft; server returns committed/forbidden/conflict states. Show actor and scope. A provider cannot self-accept on behalf of the commissioner.
4. **Commissioner decision.** Show offer and mandate basis to a separate authorized human: accept, decline with reason, request change, or delegate if protocol permits. Confirm consequence. Record decision actor/time; server rechecks membership/mandate at commit time.
5. **Report delivery.** Participant submits a report and evidence metadata with source/time/access class. Label report as participant assertion; do not convert to verified. Failed/retried submissions are idempotent and visibly distinct.
6. **Review/correction.** Separate reviewer sees report and evidence items with source/coverage, can assess within a named jurisdiction, request correction, dispute, or record bounded acceptance. Community observation cannot be styled as an official finding. Corrections supersede with lineage; don't silently erase history.
7. **Return and resume.** Both accounts see only records authorized to them after reload. Action timeline has actor, action, time, before/after or linked revision, and explanation. Any pending task appears with a meaningful “what next”.

## Retrocausal delivery path: desired first-launch proof, backwards

| Needed evidence at launch | Backward dependency | UI consequence / gate |
|---|---|---|
| A reviewer can explain, correct or dispute a delivery without rewriting history | Typed outcome/evidence, source attribution, versioning, authorized review decision and audit event | Implement distinct Reported → Under review → accepted/disputed/correction-requested states only as protocol-scoped states; do not call report “fulfilled/verified.” |
| The report is meaningful and not a naked claim | Evidence metadata, safe access controls, provenance, upload/storage lifecycle and retention | Evidence list exposes source, captured/recorded time, permitted viewers, artefact availability, assessment state; absent evidence stays explicit. |
| A provider and commissioner can coordinate independently | Persistent undertaking records; distinct participant identities; actual current mandate/membership checks; durable API | UI reads/writes a server contract; second browser/account is acceptance test; optimistic updates show conflict/retry. |
| A commitment is legitimate | Need ownership/visibility and scoped offer; commissioner authority; preconditions and decisions | Separate “offer” from “accept”; show the decision owner and basis. Never infer authority from selected organization or client role. |
| A useful need exists | Real person/institution record, scope fields, privacy classification, source and goal | Form is short but specific; explicit public/participants/private; location only when needed and consented. |
| The first user knows where to start | Proven, task-focused entry and no fake activity | First screen asks “What work are you here to move?” then shows one primary action and real tasks/opportunities, not empty modules, metrics, or a graph. |
| Product is safe to open to a cohort | Registration/session behavior, database migrations, two-account isolation, rate limits, recovery/email policy, backup/restore and ops | No public launch claim before adversarial independent verification and operational evidence. Current B12 prototype is not this evidence. |

## Recommended sequence for a one-hour refinement session

1. **First 10 minutes: choose the single first-launch undertaking and user pair.** Name a real commissioner/provider pair, domain/jurisdiction, privacy constraints and what counts as success. Avoid product-wide visual opinions without a real task.
2. **Next 15: storyboard four states:** discover need → inspect → offer/accept → report/review. Sketch desktop two-pane and phone single-pane. Decide exact status/authority/evidence language.
3. **Next 15: critique source against the storyboard.** Label each state `NOW`, `MISSING`, or `MISLEADING`; remove dead buttons/metrics; pick shared components. Do not imply a single-agent local demo is the first launch.
4. **Next 15: refine one screen prototype only** (likely the undertaking detail + task queue) using existing Angular tokens and genuine record hierarchy. No fake datasets or decorative network graph.
5. **Final 5: agree binary acceptance criteria and defer production gates explicitly.** A visually polished prototype is not multi-user launch readiness.

## Decisions for the refinement session

- Which first domain/protocol and which real commissioner/provider pair make the story concrete?
- Should first launch expose discovery to the public, members of an institution, or invite-only participants? This remains an undecided account/access policy.
- What constitutes review authority and which evidence can be collected lawfully/safely for this domain?
- Which minimum persistent workflow should be implemented first: report-only pilot with scoped public/private visibility, or full offer/commissioner acceptance/review loop? The current API has no undertaking endpoints.
