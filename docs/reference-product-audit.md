# APT-LABS Reference Product Audit

**Status:** Research snapshot, 2026-11-25. Public pages were inspected with Dembrandt and Chromium; product behavior is documented-source evidence unless explicitly marked as observed. Authenticated product experiences were not accessed. This audit is not a claim of a complete competitor teardown or superiority.

## Method and limits

- Read public official product/framework documentation and open-source repositories where available.
- Ran Dembrandt 0.41.0 against seven public landing/product-information sites using installed Chromium via CDP. The Palantir Object Explorer documentation and embedded product screen were separately inspected at 1280 × 800. No credentials were used; no tenant authentication was bypassed.
- Public visual extraction reveals rendered styles, not private workspace interaction behavior. Product UX findings below cite official product docs or source references.
- The 36 files in `docs/design/imagesinspo/` were reviewed as design inspiration. They are not treated as proven screenshots of the named products; several depict mockups, concept screens, or public dashboards.

## Cross-reference conclusions

1. **Navigation:** preserve the Angular six-surface shell as current orientation. Add contextual navigation (saved, recent, assigned) only when backed by real records and permission-aware counts. Specialist experiences remain views over the same records.
2. **Entity/detail:** combine a scan-first table/list with a selected-record detail inspector. Stable identity, type, scope, status, source, and actions should be visible without opening several apps.
3. **History/provenance:** show an attributable event stream, distinguish valid time from recorded time where needed, and make corrections append/supersede rather than erase consequential history.
4. **Authorization:** explain why an action is or is not available, but enforce it server-side on every read/write. Membership and mandate are scoped; a client role or selected organization is not authority.
5. **Workflow:** action cards should state actor, permission/mandate, preconditions, evidence expected, decision owner, emitted event, and exceptions. Do not impose one linear lifecycle across protocols.
6. **Search/views:** provide query, filter, sort, saved views, and contextual actions against authorized projections. Filters never substitute for access control.
7. **Intelligence:** present source coverage, time window, uncertainty, and methodology; recommendations remain recommendations. Do not invent values when no data exists.
8. **Mobile/offline:** start with responsive read/entry and safe interruption recovery. Offline sync is a later capability requiring an explicit threat model and conflict/retention proof.
9. **APIs/extensibility:** version protocol and API contracts; preserve stable IDs and provenance; integrations use scoped identities and deterministic idempotency. No plugin marketplace or runtime protocol registry is authorized merely by the architecture.

## Decision matrix summary

- **Replicate:** high-quality search and filter affordances, dense but readable lists, contextual detail, related-record links, attributable timelines, explainable transition actions, retryable deterministic automation, responsive/low-bandwidth interactions.
- **Adapt:** graph exploration, process stages, data-driven forms, offline sync, dashboards, object actions, and analytics only when they preserve B13's typed shared graph, local authority, consent, privacy, and evidence distinctions.
- **Reject:** universal workflow stages; people scored/ranked as assets; private product assumptions represented as observed fact; AI recommendation as decision; arbitrary business metrics without real data; disconnected mini-app stores; decorative graphs; silent sync conflict replacement; shipping authorization inferred from a role label.
- **Can do better:** keep individuals and communities in control of attribution and sharing; make plural provenance/disagreement and correction visible; bring work, capability, resources, institutions, outcomes, and knowledge together without converting all participation into CRM or ticket abstractions; optimize for East African devices/connectivity and locally governed protocols.

## Limitations and next evidence

This snapshot covers public official docs and public site pages; it does not authenticate into commercial products, claim parity across editions, exhaust APIs, test competitor mobile apps, or validate implementation claims independently. Firecrawl CLI is installed but its service rejected unauthenticated access from the current proxy network; a private API key was supplied to the app but could not be bridged into the global CLI without exposing it. Dembrandt extraction succeeded via local Chromium over CDP after its bundled browser download failed due CDN DNS/reset errors.
